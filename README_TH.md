# Supabase Web Care v1.13

ชุดเครื่องมือและสกิลสำหรับดูแลเว็บที่ใช้ Supabase หรือ PostgreSQL แบบอ่านอย่างเดียว ใช้ตรวจ key ที่หลุดในโค้ด นโยบาย RLS สิทธิ์ของฟังก์ชัน และสิ่งที่ผู้ใช้ที่ไม่ล็อกอินอ่านได้ ข้อมูลในแถวของตารางจะไม่ถูกอ่านในทุกขั้นตอน

## อ่านก่อนใช้

- **ทดสอบกับโครงการจริงสองแห่งของผู้เขียนเท่านั้น** ที่เหลือทดสอบกับฐานจำลอง โครงการที่มีโครงสร้างต่างออกไปอาจเจอส่วนที่ยังไม่เรียบร้อย ให้ลองกับ staging ของตัวเองก่อน
- **ช่องทาง `--via-api` ไม่ตรวจกฎ RLS** เว็บ Supabase ส่วนใหญ่ให้หน้าเว็บอ่านเขียนตารางโดยตรงและอาศัย RLS สำหรับเว็บแบบนั้นการตรวจกฎ RLS คือส่วนที่สำคัญที่สุด ซึ่งทำได้จากไฟล์ SQL หรือจากการเชื่อมต่อฐานข้อมูลโดยตรงเท่านั้น (ผ่าน pgrls) ในรายงานของช่องทาง `--via-api` บรรทัด `rls_live` จะเป็น NOT_RUN อย่าอ่านส่วนที่เหลือของรายงานว่าครอบคลุมตารางของคุณแล้ว การเพิ่ม `--with-advisors` จะดึงผลตรวจความปลอดภัยของ Supabase เองมาด้วย ซึ่งมีหลายข้อเกี่ยวกับ RLS (ไม่เปิด RLS, policy ที่ผ่านทุกกรณี) ช่วยให้ช่องโหว่แคบลง แต่ไม่ใช่การวิเคราะห์ policy แบบ pgrls
- **ไม่ได้รับรองมาตรฐานใด** การตรวจอิงคำแนะนำของ Supabase เอง ไม่ได้เทียบกับ OWASP กฎหมายคุ้มครองข้อมูลส่วนบุคคล หรือมาตรฐานด้านข้อมูลสุขภาพ รายงานที่ผ่านไม่ใช่หลักฐานว่าระบบได้มาตรฐาน
- **รายงานที่ไม่พบปัญหาไม่ได้แปลว่าเว็บปลอดภัย** เครื่องมือรายงานเฉพาะสิ่งที่ตรวจ และแสดงสิ่งที่ไม่ได้ตรวจเป็น NOT_RUN ทุกข้อ ไม่ทดแทนการตรวจโดยคนที่รู้จักระบบ

## เริ่มใช้งาน

ต้องมี Python 3.11 ขึ้นไป

```bash
cd supabase-web-care
python -m venv .venv && . .venv/bin/activate
pip install --require-hashes -r requirements.lock
```

### ตรวจจากไฟล์ (ไม่ต้องมี key หรือการเชื่อมต่อใด ๆ)

```bash
python -m webcare check --repo <โฟลเดอร์โค้ดของเว็บ> --migrations <โฟลเดอร์ migration>
```

ผลอยู่ที่ `webcare-output/report.md` และ `report.json` รายงานเป็นภาษาอังกฤษโดยตั้งต้น ถ้าต้องการภาษาไทยให้เพิ่ม `--lang th` หรือตั้งตัวแปร `WEBCARE_LANG=th` ไว้ครั้งเดียว ข้อความของแต่ละข้อที่พบเป็นภาษาอังกฤษทั้งสองแบบ ไฟล์ที่ชื่อขึ้นต้นด้วย `ROLLBACK_` จะถูกข้าม ถ้าลำดับชื่อไฟล์ไม่ตรงกับลำดับที่รัน migration จริง ให้ระบุทีละไฟล์ด้วย `--sql-file` แทน

การตรวจจากไฟล์รันกฎของ pgrls ได้ไม่ครบ กฎเกี่ยวกับฟังก์ชัน `SECURITY DEFINER`, view และ default privileges ต้องอ่านจากฐานข้อมูล รายงานจะระบุชื่อกฎที่ไม่ได้รันทุกครั้ง

ส่วนสิทธิ์ของฟังก์ชัน เครื่องมือตรวจจากไฟล์เองได้ (การตรวจ `functions_static`) โดยไล่คำสั่ง CREATE FUNCTION, GRANT, REVOKE, ALTER FUNCTION และ DROP FUNCTION ตามลำดับไฟล์ แล้วรายงานฟังก์ชัน `SECURITY DEFINER` ที่

- ยังเปิดให้ `PUBLIC` เรียกได้ รวมกรณีที่ถอนสิทธิ์จาก `anon` อย่างเดียว ซึ่งไม่ได้ปิดอะไร
- ถอนจาก `PUBLIC` แล้วแต่ไม่ได้ถอนจาก `anon` ซึ่งบน Supabase ยังเรียกได้ผ่านสิทธิ์ตั้งต้นของ schema
- ใช้ `current_user` ในโค้ด ซึ่งในฟังก์ชันแบบนี้หมายถึงเจ้าของฟังก์ชัน ไม่ใช่ผู้เรียก
- ไม่ได้ตั้ง `search_path`

โครงการที่มี migration เก่าอยู่แล้วเริ่มใช้ได้โดยไม่ต้องแก้ของเก่าก่อน: รันครั้งแรกด้วย `--write-baseline webcare-baseline.json` เพื่อบันทึกข้อที่พบอยู่เดิม แล้วรันครั้งต่อไปด้วย `--baseline webcare-baseline.json` รายงานจะนับเฉพาะข้อที่เพิ่มใหม่ และบอกจำนวนข้อที่ถูกยกเว้นไว้ทุกครั้ง baseline ใช้ได้กับการตรวจจากไฟล์ SQL เท่านั้น key ที่หลุดและข้อที่พบจากระบบจริงยกเว้นด้วยวิธีนี้ไม่ได้ ดูวิธีต่อเข้า CI ที่ `docs/CI_TH.md`

ใช้ขั้นนี้ตรวจ migration ใหม่ก่อนนำไปรัน ผลขึ้นกับลำดับไฟล์ ถ้าไฟล์ที่ถอนสิทธิ์ถูกอ่านก่อนไฟล์ที่สร้างฟังก์ชัน จะถือว่ายังเปิดอยู่

### ตรวจจากฐานข้อมูล

1. ให้ผู้ดูแลฐานข้อมูลรัน `sql/auditor-role.sql` แล้วตั้งรหัสผ่านตามขั้นที่ 2 ในไฟล์
2. คัดลอก `webcare.example.toml` เป็น `webcare.toml` แล้วประกาศเป้าหมาย
3. ตั้งค่าการเชื่อมต่อผ่านตัวแปรสภาพแวดล้อม แล้วรัน

```bash
export WEBCARE_DATABASE_URL='postgresql://webcare_auditor:<รหัสผ่าน>@<host>:<port>/<database>'
python -m webcare preflight --target <ชื่อเป้าหมาย>     # ดูว่า role นี้ทำอะไรได้บ้าง
python -m webcare check --target <ชื่อเป้าหมาย> --repo <โฟลเดอร์โค้ด> --migrations <โฟลเดอร์ migration>
```

การตรวจจากฐานข้อมูลจะรายงานฟังก์ชัน `SECURITY DEFINER` ทุกตัวที่ผู้ไม่ล็อกอินเรียกได้ (การตรวจ `functions_live`) เมื่ออ่านโค้ดของแต่ละตัวแล้ว ให้ใส่ตัวที่ตั้งใจเปิดไว้ใน `expected_anon_functions` ของเป้าหมายนั้นใน `webcare.toml` หลังจากนั้นฟังก์ชันอื่นที่เปิดให้ผู้ไม่ล็อกอินจะถูกรายงานที่ระดับสูง และรายการที่ผู้ไม่ล็อกอินเรียกไม่ได้แล้วจะถูกรายงานด้วย จึงใช้ตรวจซ้ำหลังทุกการแก้เพื่อดูว่าไม่มีอะไรเปิดเพิ่มหรือหายไป

ถ้าเป้าหมายประกาศ `rest` และตั้ง `WEBCARE_ANON_KEY` เป็น key สาธารณะ (anon หรือ publishable) เครื่องมือจะส่งคำขอแบบ HEAD ตารางละหนึ่งครั้งเพื่อดูว่าผู้ใช้ที่ไม่ล็อกอินเห็นแถวหรือไม่ คำขอแบบ HEAD ไม่มีเนื้อหาตอบกลับ จึงไม่มีข้อมูลแถวใดถูกดาวน์โหลด

### เมื่อเครื่องต่อฐานข้อมูลไม่ได้

บางเครื่องออกเน็ตได้เฉพาะการเชื่อมต่อแบบเว็บ จึงต่อ Postgres ไม่ได้เลย มีสองทาง ทั้งสองใช้ "ภาพถ่ายโครงสร้าง" ซึ่งเป็นผลของคำสั่ง SELECT อ่านอย่างเดียวหนึ่งคำสั่ง

**ทางที่ 1: ให้เครื่องมือดึงเองผ่าน Management API ของ Supabase (สะดวกกว่า)**

ประกาศ `project_ref` ของเป้าหมายใน `webcare.toml` แล้วรัน

```bash
export WEBCARE_ACCESS_TOKEN='<access token ของบัญชี>'
python -m webcare check --target <ชื่อเป้าหมาย> --via-api --skip secrets --skip static
unset WEBCARE_ACCESS_TOKEN
```

- เครื่องมือส่งคำขอไม่เกิน 5 ครั้ง คือคำสั่งถ่ายภาพ 1 ครั้ง คำสั่งตรวจ Storage ไม่เกิน 2 ครั้ง และคำสั่งตรวจงานตั้งเวลาไม่เกิน 2 ครั้ง ทุกคำสั่งเป็น SELECT เดียวที่เครื่องมือสร้างเอง ส่งไปที่ช่องทางแบบอ่านอย่างเดียวของโปรเจกต์นั้น (`/database/query/read-only`) ซึ่ง Supabase รันด้วย role `supabase_read_only_user` การเขียนจึงถูกปฏิเสธที่ฝั่ง Supabase ไม่ว่าเครื่องมือจะส่งอะไรไป นอกจากคำขอ GET ที่ต้องสั่งเปิดเองสามตัวด้านล่าง เครื่องมือไม่เรียกช่องทางอื่น และไม่รับ SQL จากภายนอก
- **Storage (การตรวจ `storage_buckets`)** รายงาน bucket ที่เปิดสาธารณะโดยไม่ได้ประกาศไว้ใน `expected_public_buckets` (ปานกลาง) bucket ที่ policy ให้ผู้ไม่ล็อกอินเขียนไฟล์ได้ (ปานกลาง) หรืออ่านได้ทั้งที่เป็น bucket ส่วนตัว (ต่ำ) bucket ที่ไม่จำกัดขนาดและชนิดไฟล์ (ต่ำ) และ policy ของ `storage.objects` ที่ไม่ระบุ bucket จึงมีผลกับทุก bucket เครื่องมืออ่านเฉพาะรายการ bucket กับข้อเท็จจริงของ policy ไม่อ่านแถวของ `storage.objects` จึงไม่เห็นชื่อไฟล์หรือเนื้อหาไฟล์ ได้ผลเมื่อใช้ `--via-api` เช่นเดียวกับงานตั้งเวลา
- **งานตั้งเวลา (การตรวจ `health_cron`)** รายงานงาน pg_cron ที่รอบล่าสุดล้ม (ปานกลาง) เคยล้มในช่วงที่ดู (ต่ำ) หรือเปิดใช้อยู่แต่ไม่มีรอบใดเริ่มเลย (ต่ำ) ดูย้อนหลัง 7 วัน เปลี่ยนได้ด้วย `--cron-days` ฐานที่ไม่มีงานเลยจะผ่านการตรวจนี้ ถ้าระบบควรมีงานประจำ ให้ประกาศชื่อไว้ใน `expected_cron_jobs` ของเป้าหมาย งานที่ประกาศไว้แต่ไม่มีหรือถูกปิดจะถูกรายงานระดับปานกลาง เครื่องมืออ่านเฉพาะชื่องาน ตารางเวลา จำนวนรอบ และเวลา ไม่อ่านคำสั่งที่งานรันและข้อความผลลัพธ์ เพราะสองช่องนั้นอาจมี key หรือข้อมูลจริง การตรวจนี้ได้ผลเมื่อใช้ `--via-api` เท่านั้น ถ้าต่อฐานด้วย role `webcare_auditor` จะได้ NOT_RUN เพราะ pg_cron ให้แต่ละ role เห็นเฉพาะงานของตัวเอง
- **ผลตรวจความปลอดภัยของ Supabase เอง (การตรวจ `advisors`)** ทำเมื่อเพิ่ม `--with-advisors` เท่านั้น เครื่องมือส่งคำขอ GET อีก 1 ครั้งเพื่ออ่านผลของ Security Advisor ซึ่งมีแต่ชื่อข้อที่พบและชื่อวัตถุที่ถูกชี้ token ต้องมีสิทธิ์ `advisors_read` แต่ละข้ออาจชี้วัตถุเป็นร้อย รายงานจึงแสดงจำนวนกับชื่อไม่กี่ตัวแรก ข้อที่เจ้าของตรวจแล้วและยอมรับ (เช่น ฟังก์ชันที่ผู้ล็อกอินเรียกได้ซึ่งเป็นการออกแบบ) ให้ใส่ชื่อไว้ใน `advisors_ignore` ของเป้าหมาย ข้อที่ยกเว้นจะถูกนับในหมายเหตุ ไม่ถูกซ่อน และห้ามเพิ่มรายการเพื่อให้ข้อใหม่หายไป
- **backup (การตรวจ `health_backups`)** ทำเมื่อเพิ่ม `--with-backups` เท่านั้น เครื่องมือส่งคำขอ GET อีก 1 ครั้งเพื่ออ่านรายการ backup ของโปรเจกต์ ซึ่งมีแต่วันที่และสถานะ แล้วรายงานเมื่อไม่มี backup ที่สำเร็จเลย (สูงถ้าเป็นข้อมูลจริง ต่ำถ้าเป็นข้อมูลสมมติ) backup ล่าสุดเก่ากว่า 48 ชั่วโมงโดยไม่ได้เปิด point-in-time recovery หรือรอบล่าสุดล้ม token ต้องมีสิทธิ์ `backups_read` เพิ่มอีกหนึ่งข้อ การมี backup ในรายการไม่ได้แปลว่ากู้คืนได้จริง การลองกู้คืนยังเป็นงานที่คนต้องทำ
- **สรุป log (การตรวจ `health_logs`)** ทำเมื่อเพิ่ม `--with-logs` เท่านั้น เครื่องมือส่งคำขอ GET อีก 1 ครั้งพร้อมคำสั่งนับยอดที่กำหนดตายตัว นับคำขอ 24 ชั่วโมงล่าสุดแยกตามบริการ ชื่อตารางหรือฟังก์ชัน วิธีเรียก รหัสผลลัพธ์ ชนิดของ key และล็อกอินหรือไม่ แล้วรายงาน server error (5xx) คำขอที่ถูกปฏิเสธจำนวนมาก (401/403) และฟังก์ชันที่ถูกเรียกสำเร็จโดยไม่ล็อกอินทั้งที่ไม่อยู่ใน `expected_anon_functions` คำสั่งนี้ไม่ขอ IP รหัสผู้ใช้ query string ค่า header หรือเนื้อหาคำขอ และตัดชื่อไฟล์ของ Storage ออก token ต้องมีสิทธิ์ `analytics_logs_read` เพิ่มอีกหนึ่งข้อ Supabase เก็บ log ไว้จำกัดวันตามแผนที่ใช้ การตรวจนี้จึงเห็นย้อนหลังได้ 24 ชั่วโมงต่อครั้ง
- **การตั้งค่าล็อกอิน (การตรวจ `auth_config`)** ทำเมื่อเพิ่ม `--with-auth-config` เท่านั้น เครื่องมือส่งคำขอ GET อีก 1 ครั้งเพื่ออ่านการตั้งค่าของ Supabase Auth แล้วรายงานการเปิดให้สมัครเองที่ไม่ได้ประกาศ (`expected_open_signup`) การล็อกอินแบบไม่ระบุตัวตน การไม่ยืนยันอีเมล รหัสผ่านสั้น การไม่ตรวจรหัสผ่านที่รั่ว ไม่มีการยืนยันสองชั้น token อายุยาว การไม่หมุน refresh token session ที่ไม่หมดอายุ และรายการ redirect ที่กว้างเกินไป **คำตอบของปลายทางนี้มีค่าลับปนมาด้วย** (รหัสของระบบส่งอีเมล secret ของ OAuth และ hook) เครื่องมือจึงคัดเฉพาะการตั้งค่าตามรายการที่กำหนดไว้ แล้วทิ้งส่วนที่เหลือทันทีโดยไม่อ่าน ไม่เก็บ และไม่แสดง ค่าลับเหล่านั้นยังผ่านหน่วยความจำของเครื่องที่รันชั่วขณะ จึงควรรันบนเครื่องที่ไว้ใจได้เท่านั้น token ต้องมีสิทธิ์ `auth_config_read`
- **เครื่องมืออ่าน token จากตัวแปร `WEBCARE_ACCESS_TOKEN`** ไม่ใช่ `SUPABASE_ACCESS_TOKEN` ซึ่งเป็นชื่อที่ Supabase CLI ใช้ และบนเครื่องของนักพัฒนามักเป็น token ระดับบัญชีที่เขียนฐานได้ การตรวจต้องได้ token แคบของตัวเอง ไม่หยิบ token กว้างที่บังเอิญตั้งค่าไว้ ห้ามใช้ token แบบ classic หรือ token ระดับองค์กรกับเครื่องมือนี้
- **token ทำได้มากกว่าชื่อสิทธิ์** จากการใช้จริงเมื่อ 22 พ.ย. 2569 token แบบ fine-grained ที่เลือก Database Read อย่างเดียว อ่านรายการ backup, log (มี IP ของผู้ใช้) และการตั้งค่าล็อกอิน (มีค่าลับ) ได้ทั้งหมด ให้ปฏิบัติต่อ token นี้เหมือน key ระดับผู้ดูแล: โปรเจกต์เดียว อายุสั้นที่สุด เก็บในตัวแปรสภาพแวดล้อมเท่านั้น และเพิกถอนทันทีที่รันเสร็จ
- token เป็นสิทธิ์ที่แรงกว่า role ตรวจสอบ ผ่านช่องทางเดียวกันนี้ token อ่านแถวข้อมูลในตารางได้ แม้เครื่องมือจะไม่เคยขอ ให้สร้าง token แบบจำกัดสิทธิ์ (fine-grained) ที่ใช้ได้กับโปรเจกต์เดียวและมีสิทธิ์ `database_read` อย่างเดียว ตั้งอายุสั้น และเพิกถอนเมื่อเสร็จ
- เป้าหมายที่เป็น production หรือเก็บข้อมูลจริงต้องใส่ `--owner-approved` เหมือนการตรวจแบบเชื่อมต่อ

**ทางที่ 2: ให้ผู้ดูแลรันคำสั่งเองแล้วส่งไฟล์ (เครื่องมือไม่ถือรหัสใดเลย)**

ให้ผู้ดูแลรันคำสั่งผ่านช่องทางที่มีอยู่แล้ว (เช่น SQL Editor) บันทึกผลเป็นไฟล์ แล้วให้เครื่องมือตรวจจากไฟล์นั้น

```bash
python -m webcare snapshot-sql --target <ชื่อเป้าหมาย> > snapshot.sql   # พิมพ์คำสั่ง ไม่ติดต่อที่ใด
# ผู้ดูแลรัน snapshot.sql แล้วบันทึกผลลัพธ์ JSON ทั้งก้อนเป็นไฟล์ เช่น staging.json
python -m webcare check --snapshot staging.json --target <ชื่อเป้าหมาย> --skip secrets --skip static
```

- คำสั่งเป็น SELECT เดียวที่อ่านเฉพาะ catalog ของระบบ สร้างจาก SQL ชุดเดียวกับที่การตรวจแบบเชื่อมต่อใช้ ผลจึงตัดสินเหมือนกัน
- ไฟล์ที่ได้มีชื่อ schema, ตาราง, policy และฟังก์ชัน กับค่าใช่/ไม่ใช่ ไม่มีโค้ดของฟังก์ชัน ไม่มีเงื่อนไขของ policy และไม่มีแถวข้อมูล
- ไฟล์มีป้ายชื่อเป้าหมายฝังอยู่ เครื่องมือปฏิเสธถ้าป้ายไม่ตรงกับ `--target` เพื่อกันการเอาผลของฐานหนึ่งไปเทียบกับรายชื่อที่อนุญาตของอีกฐาน เครื่องมือตรวจไม่ได้ว่าไฟล์มาจากฐานใดจริง ผู้ที่รันคำสั่งต้องรับผิดชอบป้ายนั้น
- ไฟล์ภาพถ่ายไม่มีข้อมูลของ Storage งานตั้งเวลา backup log และการตั้งค่าล็อกอิน การตรวจเหล่านั้นต้องใช้ทางที่ 1
- ทั้งสองทางรัน pgrls กับฐานไม่ได้ แถว "นโยบาย RLS จากฐานข้อมูล" จะเป็น NOT_RUN ส่วนการตรวจเพิ่มจาก catalog และการตรวจฟังก์ชันทำงานครบ
- ถ้าเป้าหมายประกาศ `rest` และตั้ง `WEBCARE_ANON_KEY` การตรวจด้วย HEAD ยังทำงานได้ โดยใช้รายชื่อตารางจากไฟล์

## ด่านกันพลาด

เครื่องมือจะปฏิเสธและไม่เชื่อมต่อในกรณีต่อไปนี้

- เป้าหมายไม่ได้ประกาศใน `webcare.toml` หรือค่าการเชื่อมต่อชี้ไปคนละที่กับที่ประกาศ
- เป้าหมายเป็น production หรือเก็บข้อมูลจริง แต่ไม่ได้ใส่ `--owner-approved` (ใส่ได้เมื่อเจ้าของระบบอนุมัติเป้าหมายนั้นด้วยคำพูดของตัวเองแล้วเท่านั้น)
- role ที่ใช้เชื่อมต่อเป็น superuser ข้าม RLS ได้ หรือเขียนตารางของแอปได้
- key ที่ให้มาไม่ใช่ key สาธารณะ
- pgrls ที่ติดตั้งไม่ใช่เวอร์ชันที่ตรวจสอบแล้ว (0.57.1)
- ไฟล์ภาพถ่ายโครงสร้างมีป้ายไม่ตรงกับเป้าหมาย ยังใช้ป้ายตั้งต้น หรือไม่ครอบคลุม schema ของเป้าหมาย
- ใช้ `--via-api` แต่เป้าหมายไม่ได้ประกาศ `project_ref` หรือค่าที่ให้มาเป็น key ของโปรเจกต์ (secret, service_role, publishable) แทนที่จะเป็น access token ของบัญชี

รหัสผ่านและ key รับผ่านตัวแปรสภาพแวดล้อมเท่านั้น และไม่ปรากฏในรายงาน ข้อความแจ้งข้อผิดพลาด หรือรายการ process

## การอ่านผล

- `NOT_RUN` และ `ERROR` แปลว่ายังไม่รู้ผล ไม่ได้แปลว่าปลอดภัย
- ระดับความรุนแรงของ pgrls เป็นคำแนะนำทั่วไปของ Postgres ต้องอ่านเทียบกับการออกแบบของระบบก่อน เช่น ตารางที่เปิด RLS ไว้โดยไม่มี policy และเข้าถึงผ่านฟังก์ชันเท่านั้น จะได้ SEC009 และ SEC002 ทั้งที่เป็นการออกแบบโดยตั้งใจ
- ผล "RLS ไม่ได้เปิด" (SEC001, SEC032) จากการตรวจไฟล์จะผิดได้เมื่อชุดไฟล์ไม่ครบประวัติ เช่น มีไฟล์ที่สร้างตารางแต่ไม่มีไฟล์ที่เปิด RLS ให้ยืนยันกับฐานข้อมูลก่อนเสมอ
- **ห้ามนำ SQL ที่เครื่องมือแนะนำไปรันทันที** ให้ถือเป็นร่างสำหรับคนตรวจ
- ทุกรายงานมีรายการที่ต้องตรวจด้วยมือ 11 ข้อ วิธีตรวจอยู่ใน `skills/supabase-web-care/references/manual-checklist.md`

ถ้าต้องการปิดกฎหรือยกเว้นวัตถุบางตัวหลังตัดสินใจแล้ว ให้เขียน `pgrls.toml` แล้วส่งด้วย `--pgrls-config` เช่น

```toml
[lint.rules.SEC016]
allowlist = ["service_role"]   # service_role ข้าม RLS ได้ตามการออกแบบของ Supabase
```

## ข้อจำกัด

- ตัวสแกน key ดูเฉพาะไฟล์ในโฟลเดอร์ ไม่ดูประวัติ git key ที่เคย commit แล้วลบออกยังอยู่ในประวัติและต้องเปลี่ยนใหม่
- การตรวจสิทธิ์ anon ทดสอบกับเซิร์ฟเวอร์จำลองเท่านั้น ยังไม่ได้ทดสอบกับ PostgREST ของจริง ดูรายการ "ยังไม่ทดสอบ" ใน `docs/OFFLINE_VM_TH.md`
- Security Advisor ต้องต่ออินเทอร์เน็ต จึงรันแยกผ่าน Supabase MCP หรือ CLI
- การตรวจฟังก์ชันดูเฉพาะสิทธิ์ EXECUTE และรูปแบบในโค้ด ไม่ได้ตัดสินว่าโค้ดของฟังก์ชันตรวจผู้เรียกถูกต้องหรือไม่ ฟังก์ชันที่อยู่ใน `expected_anon_functions` ยังต้องมีคนอ่านโค้ด
- การสรุป log ดูย้อนหลังได้ 24 ชั่วโมงและนับจำนวนคำขอเท่านั้น จึงบอกไม่ได้ว่าฟังก์ชันที่เคยเปิดอยู่ถูกเรียกไปก่อนช่วงนั้นหรือไม่ วิธีดูย้อนหลังไกลกว่านั้นอยู่ในรายการที่ต้องตรวจด้วยมือ
- role `webcare_auditor` เข้าถึงสิ่งที่ GRANT ให้ `PUBLIC` ได้เหมือนทุก role เครื่องมือรายงานวัตถุเหล่านั้นแต่ไม่เรียกใช้

## ใช้ร่วมกับอะไร

เครื่องมือนี้เป็นชั้นบาง ๆ ที่ออกแบบให้ใช้คู่กับสิ่งเหล่านี้ ไม่ได้มาแทน

- **[pgrls](https://github.com/pgrls/pgrls)** คือตัววิเคราะห์ RLS ที่เครื่องมือนี้เรียกใช้ เว็บที่ให้โค้ดฝั่งเบราว์เซอร์อ่านเขียนตารางโดยตรงควรใช้ pgrls เองด้วย คือ lint migration ใน CI และรัน `pgrls verify` กับฐาน staging หรือ branch ของ Supabase โหมด probe ของ pgrls จะ INSERT แถวทดสอบใน transaction แล้ว rollback และต้องใช้ role ระดับผู้ดูแล จึงไม่ควรใช้โหมดนั้นกับระบบจริง
- **Security Advisor ของ Supabase** (หน้า Dashboard, คำสั่ง `supabase db advisors` หรือเครื่องมือ MCP `get_advisors`) เป็นการตรวจของแพลตฟอร์มเอง และเห็นสิ่งที่เครื่องมือนี้ไม่เห็น ควรรันทุกครั้ง รายงานจะแสดงข้อนี้เป็นยังไม่ได้ตรวจ เพราะเครื่องมือเรียกแทนไม่ได้
- **สกิลทางการของ Supabase** คือ `supabase` และ `supabase-postgres-best-practices` สกิลใน repo นี้บอกให้ agent เปิดอ่านสองตัวนั้น แล้วเพิ่มวิธีทำงานกับข้อห้ามทับลงไป
